## 1. 認証・認可

### 1.1 認証

| 利用者 | 方式 | 備考 |
| --- | --- | --- |
| 社員 | 社員番号＋パスワード（M_EMPLOYEE.PASSWORD_HASH と照合） | 社内認証基盤（SSO）と連携する場合は差し替える。パスワードはソルト付きハッシュ（PBKDF2 または bcrypt）で保持 |
| 顧客 | 確認用 URL のトークン | ログインなし。トークンは 1 回の確認依頼ごとに発行し、SHA-256 ハッシュで保持。有効期限 14 日（仮） |
| 外部システム | API キー（HTTP ヘッダ）＋接続元 IP 制限 | キーは設定ファイルで管理し、リポジトリには含めない |

- 社員のセッションはログイン成功時に再生成する（セッション固定化対策）。タイムアウトは 30 分（仮）。
- ログイン失敗が連続 5 回（仮）でアカウントをロックし、管理者が解除する。ロック状態の保持方法は詳細設計で決める（M_EMPLOYEE への列追加を想定）。

### 1.2 認可（権限）

| 機能・画面 | 01 担当者 | 02 承認者 | 09 管理者 |
| --- | --- | --- | --- |
| 申込一覧・詳細の参照 | 自分が担当の申込 | 自分が承認明細に含まれる申込と自部署の申込（仮） | 全申込 |
| 入力・修正・確定・申請・引戻し・審査中修正・修正対応・契約変更 | ○（担当の申込のみ） | × | × |
| 承認・差戻し | × | ○（現在ステップの承認者のみ） | × |
| 一括取込 | ○ | × | × |
| 確認依頼メール再送・外部連携再送 | ○（担当の申込のみ） | × | ○（外部連携再送のみ） |
| マスタメンテナンス | × | × | ○ |

- 画面のボタン表示制御に加え、サーバ側（Filter とサービス層）で必ず権限を検証する。
- 操作主体と操作者の照合は F14 で行う（[03. 6 章](03-status-transition.md#6-操作主体と操作者の照合)）。

## 2. 排他制御

- 申込（T_APPLICATION）とマスタは行バージョン（ROW_VERSION）による楽観排他とする。画面表示時に読んだ行バージョンを hidden で持ち回り、更新時に `WHERE ROW_VERSION = :expected` で更新する。更新件数 0 なら排他エラーとし、後勝ちにしない。
- 同じ申込に対する操作は F14 が申込行を最初に更新するため、同時操作は片方が排他エラーになる。
- 子テーブル（版、承認明細、同意、外部連携）は申込の排他に従う。単独で更新する場合（バッチの送信状態更新など）は自身の行バージョンで排他する。
- 排他エラー時のメッセージ：「他のユーザーが更新しました。最新の内容を確認してください。」

## 3. トランザクション

- 画面・IF は 1 リクエスト 1 トランザクション。サービス層の入口で開始し、正常終了でコミット、例外でロールバックする。
- F14 の後続処理（通知・外部連携の登録）は業務トランザクションに含める。メール送信・外部送信そのものはバッチが別トランザクションで行う。
- バッチは 1 行ごとにコミットする。
- 分離レベルは READ COMMITTED（SQL Server の既定）とし、SNAPSHOT 分離への変更は性能検証後に判断する。

## 5. 日付・時刻・金額・文字

| 項目 | 規則 |
| --- | --- |
| タイムゾーン | 日本時間（JST）。DB にも JST の日時をそのまま格納する（DATETIME2） |
| 日付の表示 | yyyy/MM/dd |
| 日時の表示 | yyyy/MM/dd HH:mm |
| 日付の入力 | yyyy/MM/dd（画面）、yyyy-MM-dd（CSV・IF） |
| 金額 | 円、整数、最大 13 桁。表示は 3 桁カンマ区切り、入力はカンマ許容 |
| 変更金額倍率 | 小数第 4 位まで（切り捨て）。表示は小数第 2 位まで |
| 文字コード | UTF-8（画面・DB・CSV・IF すべて） |
| 文字種 | 制御文字（改行・タブを除く）は入力不可。全角・半角の変換はしない |

## 6. 入力チェック共通

チェックは次の順序で行い、同じ項目で複数のエラーがある場合は最初のエラーだけ表示する。

1. 必須
2. 型・桁（数値、日付、最大桁数）
3. 書式（日付の妥当性、コード値の範囲）
4. 相関（契約開始日 ≦ 契約終了日 など）
5. 業務（顧客番号の存在、ステータス、権限 など。サービス層で行う）

- 前後の空白はトリムしてからチェックする。
- エラーは項目ごとにメッセージを表示し、入力値は保持する。

## 7. メッセージ

メッセージはプロパティファイルで管理し、ID で参照する。

| ID 体系 | 種別 | 例 |
| --- | --- | --- |
| I0xx | 情報 | I001「登録しました。」、I002「申請しました。」、I003「承認しました。」、I004「差し戻しました。」、I005「確定しました。」、I006「再送を登録しました。」 |
| W0xx | 警告 | W001「変更金額がしきい値を超えるため、外部事前確認の対象になります。」 |
| E0xx | 入力エラー | E001「{0}を入力してください。」、E002「{0}は{1}桁以内で入力してください。」、E003「{0}の形式が正しくありません。」、E004「契約終了日は契約開始日以降の日付を入力してください。」、E005「{0}は{1}以上の値を入力してください。」、E006「{0}はすでに登録されています。」、E007「{0}は{1}以降の日付を入力してください。」、E008「ファイルの形式またはサイズが正しくありません。」 |
| E1xx | 業務エラー | E101「現在のステータスではこの操作はできません。」、E102「他のユーザーが更新しました。最新の内容を確認してください。」、E103「この操作を行う権限がありません。」、E104「変更がないため確定できません。」、E105「差戻しにはコメントを入力してください。」、E106「社員番号またはパスワードが正しくありません。」、E107「アカウントがロックされています。管理者に連絡してください。」、E108「承認者には有効な承認者権限の社員を、会社区分をそろえて設定してください。」 |
| E2xx | 顧客向け | E201「この確認 URL は無効です。担当者にお問い合わせください。」、E202「この確認 URL は有効期限が切れています。」 |
| E9xx | システムエラー | E901「システムエラーが発生しました。管理者に連絡してください。」 |

## 8. エラー処理

| 分類 | 例 | 扱い |
| --- | --- | --- |
| 入力エラー | 必須未入力、桁超過 | 同じ画面にメッセージを表示して再入力 |
| 業務エラー | 遷移不可、排他、権限 | 業務例外として送出し、メッセージを表示。ログは INFO |
| システムエラー | DB 接続失敗、想定外の例外 | ロールバックし、CM01 システムエラー画面を表示。ログは ERROR でスタックトレース付き。利用者には内部情報を見せない |
| IF エラー | 認証失敗、電文不正 | エラーコードと HTTP ステータスで応答（[12. 外部インターフェース設計](12-external-interface.md)） |

## 9. ログ

| ログ | 内容 | 保持 |
| --- | --- | --- |
| アプリケーションログ | リクエスト単位の開始・終了、業務エラー、システムエラー。日時、レベル、ログ ID、社員 ID／顧客 ID、申込 ID を出力 | 1 年（仮） |
| 監査証跡 | ステータス履歴（T_STATUS_HISTORY）、承認明細、顧客同意（日時・IP）、外部連携の送受信日時。DB に保持 | 申込と同じ |
| IF ログ | 送受信の電文（要約）、応答コード。個人情報はマスク | 1 年（仮） |
| バッチログ | 開始・終了・処理件数・エラー件数 | 1 年（仮） |

- パスワード、トークン平文、API キーはログに出力しない。

## 10. セキュリティ

| 対策 | 内容 |
| --- | --- |
| 通信 | 全画面・IF を HTTPS にする |
| CSRF | 更新系リクエストにセッション単位のトークンを hidden で付け、Filter で検証する。顧客画面もトークンを付ける |
| XSS | JSP の出力は JSTL の `c:out` などで必ずエスケープする |
| SQL インジェクション | PreparedStatement のみ使用。動的な並び順はホワイトリストで組み立てる |
| セッション | ログイン時に再生成、Cookie は HttpOnly・Secure、タイムアウト 30 分（仮） |
| 認証情報 | パスワードはソルト付きハッシュ、トークンは SHA-256 ハッシュで保持。平文は保持しない |
| ファイルアップロード | 拡張子・サイズ（5MB、仮）・行数を検証し、サーバに保存せずメモリ上で処理する |
| HTTP ヘッダ | X-Frame-Options: DENY、X-Content-Type-Options: nosniff、Content-Security-Policy（詳細設計で決定） |
| 顧客画面 | URL 推測を防ぐため、トークンは 256 ビットの乱数。総当たり対策として失敗回数に応じた遅延を入れる（仮） |

## 11. 画面共通

- レイアウト：ヘッダ（システム名、ログイン社員名、権限、ログアウト）、メニュー（権限別）、コンテンツ、フッタ。
- 一覧は 1 ページ 20 件（仮）でページング。並び順は更新日時の降順を既定とする。
- 更新系は PRG（POST → Redirect → GET）パターンで二重送信を防ぐ。
- 顧客画面はメニューを持たず、ヘッダにシステム名のみ表示する。
- 詳細は [11. 画面設計](11-screen-design.md)。
